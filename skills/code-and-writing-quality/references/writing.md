# Writing and revision

Identify the reader, medium, and requested depth of editing. In a light edit, preserve commitments, register, and uncertainty. Changing “I think I can deliver on Friday” to “I will deliver on Friday” introduces a promise.

Draft from the available facts. Replace generic praise with a specific action, actor, or observation when the evidence supports it. Remove repetition and empty transitions. Let sentence length follow the idea. Keep passages that already read well.

Check consequential figures and quotations against the relevant source passage, including units, dates, population, and scope. When evidence is missing, omit an unnecessary claim or identify what needs confirmation. Attribute testimony to the speaker and calibrate causal claims to the study design.

Reread for added commitments, changed facts, and overstated conclusions. Assess clarity and fidelity to the author's meaning. A detector score cannot establish authorship. When asked for a ready-to-send message, return the finished text directly.

Before delivery, scan for draft instructions addressed to the user, unfilled brackets, and links that still point to a search or placeholder. Check suspect DOI or ISBN identifiers against the actual work. When prose abruptly changes register, check for a quotation, translation, or co-author before attributing the change. Formulaic contrasts, repeated groups of three, bold labels, polished grammar, stock transitions, and long dashes have little diagnostic value in isolation. Keep them when they serve the reader. For bulk-generated material sometimes called “AI slop,” assess duplication, factual accuracy, and informational value passage by passage.

## Rewriting project Markdown

Apply this guide to README files, contributor guides, changelogs, architecture notes, and other Markdown in any project. For a project-wide request, inventory the in-scope .md files, including nested documentation. For a single-file request, limit prose edits to that file. Follow the project's terminology, Markdown dialect, and requested language. If a page is generated, update its maintained source and regenerate it through the project's documented workflow.

Rewrite the prose while preserving technical meaning, prerequisites, warnings, and the order of dependent steps. Treat fenced code, CLI arguments, paths, identifiers, front matter, template directives, and diagram syntax as functional content. Change them only when the request requires it and verify changes against the project. When renaming a heading, check incoming fragment links and update their targets or retain a compatible anchor.

Review the diff for accidental changes to examples, links, tables, and task lists. Use the project's existing documentation checks when available. For a prose-only edit, compare code blocks and link destinations before and after.
